# 하늘 타일 프록시 실험 (2026-11-14, ansirh)

> 상태: **로컬 실험 완료, 적용은 팀 결정 필요.** 배포(CI·Vercel) 담당 팀원 확인이 필요해서 근거를 모아 둔다.
> 실험 코드는 커밋하지 않았다. 코드는 [`proxy-route.md`](proxy-route.md)에 있다.

## 한 줄 요약

3D 하늘을 확대했을 때 선명해지는 데 6~15초(중앙값 약 12초)가 걸린다. 원인은 브라우저가 IRSA와의 **HTTP/2 연결 하나**로 타일을 모두 받는데, 한국–IRSA(미국) 사이에서는 연결 하나의 속도가 약 250~300KB/s로 제한되기 때문이다. 타일을 우리 서버(Route Handler)를 거쳐 받게 했더니 **약 5초로 줄고 매번 비슷하게** 나왔다 (로컬 서버 기준).

## 배경

- 하늘 화면은 Aladin Lite 하나가 모든 시야를 그린다 ([결정 #29](../../decisions.md)). 하늘 이미지는 CDS 장애 때문에 IRSA가 미러한 2MASS 컬러 HiPS(`https://irsa.ipac.caltech.edu/data/hips/CDS/2MASS/Color`)를 쓴다 ([결정 #25](../../decisions.md)).
- HiPS는 512×512 JPEG 타일 피라미드다(order 0~9, 한 단계마다 해상도 2배). 1920px 화면에서 1° 시야는 order 8 타일 약 25장(장당 약 80~300KB, 합쳐서 2~4MB)이 필요하다.
- Aladin Lite는 시야에 맞는 단계의 타일을 요청하고, 도착 전에는 이미 받은 낮은 단계 타일을 늘려서 보인다. 그래서 검은 화면은 없지만 "흐릿한 시간"이 길다.

## 원인을 찾은 과정

| 의심한 원인 | 확인 방법 | 결과 |
| --- | --- | --- |
| 확대 중 쓸모없어진 타일을 취소하지 않음 | Aladin JS 글루 코드에서 wasm이 부를 수 있는 JS 함수 131개 확인, 브라우저에서 확대·축소·이동 후 요청 상태 확인 | 맞다. 취소 수단(`AbortController`)이 연결돼 있지 않고, 요청 99건이 전부 끝까지 받아짐. **하지만 핀·검색 이동에서는 중간 단계 요청이 3~4장뿐**이라 주원인이 아님 |
| 더 가까운 미러가 있음 | China-VO, IAS, CDS 미러 응답 시간 측정 | 아니다. China-VO는 IRSA보다 빠르지 않고(첫 응답 0.55~3.4초, 2016년판), IAS는 응답 없음, CDS는 404 |

| **연결 하나의 속도 한계** | 아래 측정 1, 2 | **맞다** |

## 측정

### 측정 1. 연결 수에 따른 속도 (터미널, curl)

처음 받는 order 8 타일 12장(약 1.3MB)을 연결 수를 바꿔 받았다. 재현: [`measure-parallel.sh`](measure-parallel.sh)

| 연결 수 | 1차 | 2차 (스크립트로 재측정) |
| --- | --- | --- |
| 1개 (차례로) | 4.7초 | 4.3초 |
| 6개 (동시에) | 1.3초 | 1.7초 |
| 12개 (동시에) | 1.0초 | 1.2초 |

연결 하나는 약 250~300KB/s에서 막히고, 연결을 늘리면 거의 그만큼 빨라진다. 한국–미국의 긴 왕복 시간 때문에 TCP 연결 하나의 처리량이 제한되는 경우로 보인다(왕복 시간 자체는 재지 않았다).

브라우저에서 직접 받을 때의 타일 도착 시각을 보면 0.3~0.6초 간격으로 **한 장씩 차례로** 끝났다. 연결 1개로 받을 때와 같은 모양이다.

### 측정 2. 이동 후 선명해지기까지 (브라우저)

- 조건: 하늘 화면 기본 시야(90°)에서 **한 번도 보지 않은 좌표**를 검색해 1°로 이동. 브라우저 캐시 영향을 피하려고 매번 다른 좌표를 썼다.
- 지표: 검색 실행부터 최종 단계(order 8) 타일을 마지막으로 받은 시각.
- 직접 받기와 프록시를 번갈아 측정했다. 재현: [`measure-flight.js`](measure-flight.js)
- 환경: Chrome, 1920×911 화면(devicePixelRatio 1), 서울 가정용 네트워크, `pnpm build && pnpm start` 로컬 서버.

| 방식 | 좌표 (RA, Dec) | 요청 수 | order 8 타일 | 선명해진 시각 |
| --- | --- | --- | --- | --- |
| 직접 | 275.0, −20.0 | 29 | 26 | 14.7초 |
| 직접 | 258.0, −38.0 | 28 | 24 | 13.0초 |
| 직접 | 284.0, −27.0 | 30 | 26 | 6.3초 |
| 직접 | 268.0, −24.0 | 29 | 25 | 11.8초 |
| 프록시 | 281.0, −14.0 | 29 | 26 | 5.1초 |
| 프록시 | 262.0, −44.0 | 33 | 28 | 5.9초 |
| 프록시 | 252.0, −30.0 | 29 | 26 | 5.1초 |

- **직접: 중앙값 약 12초, 6~15초로 들쭉날쭉. 프록시: 약 5초, 매번 비슷.**
- 요청 수는 같다. 바뀐 것은 타일이 오는 경로뿐이다.
- 프록시는 Node(undici)가 IRSA에 여러 연결로 동시에 받고, 브라우저와 서버 사이는 같은 네트워크라 빠르다.

## 한계

- **로컬(한국) 서버 기준이다.** Vercel에 올리면 사용자 → 서울 근처 엣지 → 함수 리전 → IRSA 경로가 된다. 함수를 IRSA(캘리포니아 패서디나)와 가까운 미국 서부 리전에 두면 함수–IRSA 구간이 더 빨라질 것으로 예상하지만, **배포해서 재 봐야 한다.**
- 약 5초가 하한일 수 있다. Aladin이 타일 요청을 약 1초 간격으로 6~8장씩 보내는 것으로 보여서 25장이면 요청에만 약 4초가 걸린다. Aladin 내부(wasm)라 확인하지 못했다.
- 측정 횟수가 직접 4회, 프록시 3회로 적다. 같은 네트워크·같은 시간대에서만 쟀다.
- 마우스 휠 확대도 같은 경로로 타일을 받으므로 효과가 있을 것으로 예상하지만, 따로 측정하지 않았다.

## 적용하려면 (팀 결정 필요)

| 항목 | 내용 | 확인할 사람 |
| --- | --- | --- |
| 공개 엔드포인트 | `/api/hips/...`가 생긴다. 실험 코드는 `properties`, `Norder*/Allsky.jpg`, `Norder*/Dir*/Npix*.jpg`만 허용하고 나머지는 404 | 팀 |
| Vercel 사용량 | 타일 1장마다 함수 1회 실행 + 전송량. 1° 화면 하나에 약 30회, 2~4MB | 배포 담당 |
| CDN 캐시 | 타일은 고정 파일(IRSA `Last-Modified` 2020년)이라 `Cache-Control: public, s-maxage=…`로 엣지에 오래 캐시하면 같은 타일은 함수가 다시 실행되지 않는다. 실험 코드는 측정 때문에 `no-store` | 배포 담당 |
| 함수 리전 | IRSA와 가까운 미국 서부를 권장 (측정 필요) | 배포 담당 |
| 측정 방법 | 지금 CI는 `main`만 프로덕션에 배포한다. 프리뷰 배포로 먼저 재 보는 것을 권장 | 배포 담당 |
| CDS 복구 후 | SPHEREx 컬러 HiPS(CDS, 프랑스)로 돌아가면 프록시 대상 주소도 바꿔야 한다 | 팀 |

적용이 정해지면 `docs/decisions.md`에 기록하고 `docs/PLAN.md` 9장("3D 하늘 구현")을 같은 커밋에서 고친다.

## 검토 후 하지 않기로 한 것

- **이동(fly) 중 타일 요청 막기** (화면을 CSS로 확대하다 도착하면 1° 타일만 요청): 이동 중 요청은 원래 3~4장(약 15%)뿐이라 효과가 작고, 정지 화면 스냅샷·전환 튐 처리로 복잡도가 크다.
- **미리 받기(사전 캐싱)**: 이번 실험 범위에서 제외했다.
